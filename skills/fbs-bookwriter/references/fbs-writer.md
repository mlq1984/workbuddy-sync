# 写作与局改方法

这是包内写作职责方法，不代表宿主已经注册名为fbs-writer的Agent。默认由当前助手按本方法执行；真实委派需使用当前会话实际提供的能力，并沿用用户授权和[主持方法](fbs-team-lead.md)指定的边界。

## 开始前

读取本次分配的章节brief、读者与用途、允许使用的材料、相关词表/前后文，以及明确的输出位置。缺少必要信息时只补问影响本次产出的关键项；可先交付标注待核的局部稿。不得自行扩大章节范围、搬动原件或改共享台账。

## 写作步骤

1. 先建立与brief对应的小提纲和证据位置。区分用户原述、可核实事实、分析、推断和未证信息；不能用流畅措辞掩盖缺来源。
2. 按提纲写有实际内容的段落：主张、依据/示例、推理、适用条件和过渡相互对应。保留约定术语、必要引用、表格/图表来源和读者所需的解释；不生成空章节或用模板填充冒充完成。
3. 涉及时效、政策、市场或专业事实时，使用实际可用且被授权的检索；没有查到可靠出处就标未知/待核，不伪造URL、引文、研究结果或置信分数。遵循[检索策略](references--05-ops--search-policy.json)。
4. 局部修改先锁定用户指定段落、变更点与保留项，输出新版本或可审阅差异；不因顺手润色覆盖未分配的正文、引用或用户手改。多任务协作只写分配的临时文件，合并由主持方负责。
5. 完成后做[S层自检](references--02-quality--quality-S.md)，核结构、段落、格式和明显语言问题；再按[P/C/B检查](references--02-quality--quality-PLC.md)列出需要进一步判断的项。不得用自检替代真实专业审校或用户确认。
6. 实际读回交付文件，确认正文、引用、编码和输出范围。未完成则标为partial，说明缺口、已有成果和可接续位置；不把计划、脚本返回0或成员自述当成用户采用。

## 输出

向用户或主持方交付：可编辑稿件、对应章节/版本、关键来源、改动范围、未证信息与需要复核的项目。只在本次授权的项目路径写入，不修改共享词表、书籍状态、生产服务、账户或发布渠道。

方法依据：本包S3写作/局改方法、章节brief与质量规则；不复用旧WritingAgent的空草稿stub，也不声称已创建独立宿主成员。
