# 置信度口径（为什么不能张口就说"准确率 95%"）

## 一、三个引擎的置信度语义完全不同

| 引擎 | 提供什么 | 能当百分比用吗 |
|---|---|---|
| Tesseract | 词级置信度 0~100，按行取平均 | **能**，这是校准过的对数概率 |
| Windows WinRT | **什么都不提供** | 不能——本实现显式留空，不编数字 |
| macOS Vision | `candidate.confidence`，**实测恒为 0.5**（任何图、任何尺度、任何语言都一样） | **不能**，它对区分识别质量毫无信息量 |

### 实测证据（Vision）

用点阵字生成的清晰测试图，分别以 scale=4/8/12、语言 `-`/`en-US` 识别，
`topCandidates(1)[0].confidence` 与 `VNRecognizedTextObservation.confidence` **全部返回 0.5**：

```
scale= 4 lang=-      conf=[0.5, 0.5]
scale= 8 lang=en-US  conf=[0.5, 0.5]
scale=12 lang=en-US  conf=[0.5, 0.5]
```

所以本技能对 Vision **不报百分比**，改用下面这个信号。

## 二、Vision 的替代信号：候选差异度

Vision 会为每个文本行返回多个候选。**首选与次选文字不同 ⇒ 该行存在歧义**。

| 情况 | 判定 | 交付动作 |
|---|---|---|
| 首选与次选文字相同 | 视为确定 | 正常输出 |
| 首选与次选文字不同 | 标为需核对 | 输出该行 + **次选文本**，让人工一眼看出分歧点 |

例：

```
TOTAL 1280. 00  <!-- 需核对：引擎给出了不同的次选结果 -->
```

文末会集中列出：

```
## 需人工核对的行
- TOTAL 1280. 00（引擎给出了不同的次选结果；次选：TOTRL I280. O0）
- INVOICE R-12345（引擎给出了不同的次选结果；次选：INVOIcE A-12345）
```

> 注意这个信号是**保守**的：字符大小写差异（`OCR` vs `OcR`）也会被标出来，
> 而对点阵字这种非常规字形，几乎每行都会命中。这不是缺陷，而是我们**宁可多提醒、
> 不假装有精确概率**的取舍。

## 三、交付时的表述规范

✅ 可以说：

- "识别出 12 行，其中 3 行存在歧义，已连同次选结果列出，建议以原图为准。"
- "Tesseract 给出的平均置信度是 64%，低于常用阈值 75%。"
- "该引擎不提供置信度，无法给出准确率估计。"

❌ 不可以说：

- "识别准确率 95%"（没有任何依据）
- "已完美识别"（OCR 不存在完美）
- "置信度 50%"（把 Vision 的恒定 0.5 当概率播报——这是误导）
- "应该没问题"（把不确定性转嫁给用户）

## 四、低置信阈值

`scripts/render.py` 中的 `LOW_CONFIDENCE = 0.75`：

- 低于该值的行在 Markdown 里加注释、在 HTML 里标红并计入「只看需核对行」；
- 需要更严或更松时改这一个常量，而不是在各处硬编码。

## 五、人工核对的操作建议

HTML 产物已内置核对流程：

1. 左图右文对照，点击任意行会在原图上高亮对应区域；
2. `j` / `k`（或方向键）逐行移动，`c` 复制当前行；
3. 点「只看需核对行」过滤掉确定的行；
4. 点「查看结构化 JSON」可复制含坐标的完整数据，便于二次处理。
